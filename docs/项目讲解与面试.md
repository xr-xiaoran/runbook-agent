# RunbookAgent 从零读懂

## 先讲清一句话

这是一个“查依据、给建议、起草工单，但不擅自执行”的故障排查助手。场景是自己的学习项目，不是已经连接公司生产环境。默认模式只是可复现演示，真实模型工具调用适配器需要配置账号后进一步验收。

## 为什么它不只是一次聊天 API

真实模式的模型每轮可以选择输出工具调用。服务端校验工具名和 JSON 参数，执行检索，把结果作为 tool 消息放回上下文，再请求下一轮；模型最终返回结构化答案。最多 6 次模型调用，避免无限循环。演示模式用固定脚本替代模型，目的是不用密钥也能测试工程链路，不能拿它证明自主规划效果。

请求 → 身份校验 → 运行循环 → search_docs/read_chunk → 证据上下文 → JSON 答案与引用校验 → 保存结果 → 用户阅读 → 独立审批 → 本地工单。

## 检索是怎样工作的

1. 内置 Markdown 按空行分段，每段有固定来源 ID。
2. 英文按词切分，中文用连续双字，如“任务超时”拆出“任务”“务超”“超时”。
3. 计算 BM25 风格分数：稀有匹配词权重更高，同一词频增长会饱和，并对文档长度归一化。
4. 返回前 3 段，交给模型作为不可信资料，而不是新指令。

优势是低依赖、可解释。缺点是同义词和隐含语义召回差；没有向量语义。没有召回证据时，运行时会拒绝无依据草稿和行动步骤，返回资料不足。只要有部分匹配也可能得到无关片段，所以仍需评测和人审。

## 引用校验解决了什么

模型不能引用从未检索过的 ID，伪造 ID 会被拒绝。但模型拿真实片段引用去支持错误结论，当前 ID 校验发现不了。面试不能说“彻底消除幻觉”。下一步应建立句子与证据支持关系的人审样本，测 groundedness，而不只测 ID 合法性。

## 为什么模型不能直接创建工单

模型只有只读工具。最终 draft 只是文本，尚未写入 tickets。人工用另一把密钥调用审批接口，明确 confirm=true，服务才保存工单。run_id 唯一约束让 12 个重复确认也只生成一张工单。

这是逻辑权限隔离，不是身份认证平台；共享审批密钥无法识别具体哪个人操作。也没有工单外发，所以不会真的通知公司同事。外发要另接接口并重新设计幂等、审计与权限。

## 模型边界与资源预算

工具白名单防止调用任意 Shell；read_chunk 只接受已知 ID，不把用户输入当文件路径。输入、输出、上下文大小和最大循环次数都有检查；同样的工具调用在一次运行内可复用缓存。全局只接受 2 个并行运行，超过返回 429。

60 秒超时是协作取消，HTTP 请求通过 context 传播。供应商 token 数只在响应后知道，超过预算时该次消费已发生，所以不是严格账单上限。网络错误不自动重试，防止不确定情况下重复付费。

## 数据保存和故障边界

SQLite 保存终态运行与轨迹，完成后重启可查。执行途中崩溃会丢掉这一轮未保存的运行；没有 checkpoint、后台恢复或历史会话记忆。trace 是耗时和工具返回证据，不是模型私有思维链。输入可能有秘密，当前只有“不提交敏感信息”的使用约束，没有可靠自动脱敏。

## 面试追问

1. Agent 和工作流区别？真实模式由模型选择工具与结束时机，运行时约束边界；演示模式则是固定流程。
2. 为什么不用框架？学习版用 Go 原生代码暴露工具协议和循环细节，便于理解和测试；不代表框架不必要。
3. 能写 RAG 吗？可以描述词法检索增强与引用，但不能写向量检索、Embedding 或 rerank。
4. 评测 100% 能代表回答准确吗？不能。当前是自编的 11 个明显匹配正例和 1 个无匹配负例，只是检索回归，不是泛化能力。
5. 怎样处理提示注入？提示中声明资料不可信，更重要的是工具没有执行权限，审批走独立路径。仍可能生成错误建议，需要人审。
6. 为什么不直接让模型输出 SQL？任意 SQL 会扩大权限与风险。当前只允许固定查询工具，写入由服务端固定接口处理。
7. 模型接口测通了吗？模拟服务协议测试通过不等于真实供应商验收，需要配置支持工具调用的模型后测试。
8. 为什么不做多智能体？当前问题用单个有界工具循环即可；多角色会增加成本、状态和评测复杂度，需要证据支持再扩展。

## 学习顺序

第一天运行 demo，查看 HTTP 请求与审批前后的区别；第二天读 model.go 的 Message、Call 和 Next；第三天读 runtime.go 工具循环并画状态流；第四天读 knowledge.go 和 eval，添加 5 个同义词问题；第五天读 Store.Approve 并运行并发测试；第六天故意伪造工具名或引用，确认运行被拒绝；第七天配置你自己的模型，记录至少 20 个真实问题、失败类型与改进，不要把密钥提交进仓库。
